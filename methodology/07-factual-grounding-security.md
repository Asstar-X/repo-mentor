# 07. 代码事实强锚定与沙箱安全

## 目标
建立技术文档真实性审计与分析陌生开源代码时的安全防护方法论。彻底杜绝大模型在代码走读过程中编造不存在的文件路径与虚拟行号，确保架构图表 100% 语法合规可渲染，并在分析不可信代码库时坚守沙箱安全底线。

---

## 1. 代码事实强锚定三原则 (Triple-Anchor Verification)

技术文档的权威性建立在真实严谨的基础之上。文档中所有引用的代码锚点推荐采用 `[path/to/file.ext#Lstart-Lend]` 格式，必须通过三道物理门禁核验：

1. **物理文件存在性 (File Existence)**：
   - 引用的相对路径必须在目标代码库根目录下实际存在；
   - 杜绝引用凭空编造的虚拟文件。
2. **行号边界合法性 (Line Bounds)**：
   - 引用行号必须在文件总行数（EOF）范围内；
   - 禁止出现倒置行号（如 `L120-L40`）或超出文件结尾的虚假行号。
3. **语义符号对齐 (Symbol Grounding)**：
   - 所标出的行号范围内，应当切实包含该处所讨论的函数、类、数据结构或核心代码切片；
   - 允许因小版本演进而带来的微小漂移，但核心语义必须严格吻合。

---

## 2. Mermaid 架构图表规范与自愈

架构白皮书中的图表必须能在无外部网络依赖的环境下稳定渲染：
- **顶格对齐规范**：````mermaid` 代码块建议从行首第 0 列开始，避免前置缩进破坏 Markdown 解析器；
- **特殊字符引号包裹**：节点标签包含括号、斜杠、空格或标点时，强制使用双引号包裹，如 `NodeA["API Gateway (port 8080)"]`；
- **状态图语法合规**：在 `stateDiagram-v2` 中，状态迁移说明必须使用冒号隔开，如 `StateA --> StateB : on_success`；
- **规避关键字冲突**：避免使用 `end` 作为节点标识符（因 `end` 为 Mermaid 保留关键字），推荐替换为 `end_node`。

---

## 3. 不可信开源代码库的安全防范原则

在精读从互联网获取的未知或第三方开源项目时，智能体与开发者必须时刻保持安全防御意识：

1. **严格将目标文件视为不可信数据**：
   - 静态分析只读取文件内容，**绝不盲目执行目标仓库内部自带的编译构建脚本、Makefile、安装脚本或预编译二进制文件**；
2. **防范投毒与代码执行陷阱**：
   - 警惕恶意的 `setup.py`、`preinstall` 钩子、环境变量劫持脚本；
   - 运行冒烟测试时，优先审查单测脚本源码本身，确保其不包含向外网络请求或破坏性文件系统操作；
3. **隔离与最小权限**：
   - 在沙箱或只读权限下进行源码静态走读与 AST 符号提取，保障本地宿主环境绝对安全。
