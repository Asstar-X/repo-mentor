# 01. 项目侦察与演进热点指南

本指南作为 `/repo-recon` 的思考工具，聚焦如何在短时间内摸清陌生项目的真实存在理由，并通过版本历史直击系统的核心重心。

---

## 1. 寻找项目的存在理由

快速理解一个陌生项目，先别陷入函数和类细节，重点抓住三个工程问题：

1. **现实痛点**：在没有这个项目前，常规做法遇到了什么麻烦？是性能瓶颈、繁琐重复还是可靠性问题？
2. **黑盒契约**：
   - 接收什么形式的输入（配置、数据结构、命令、网络请求）？
   - 最终交付什么产物（格式化输出、文件生成、状态变更）？
   - 对外产生了什么持久化影响？
3. **“30 行脚本”检验法**：
   - 如果用一段最朴素的单文件脚本去实现这个需求，在什么极端情况下会行不通？
   - 让朴素脚本崩溃或难以维护的那个场景，往往就是该项目架构设计存在的真正原因。

---

## 2. 闭环验证：快速建立运行心智

只看代码不运行容易产生理解偏差。建立理解的第一步是在本地跑通一个最小闭环：
- **最小构建**：优先使用项目原生、极简的构建或依赖安装命令；
- **定位冒烟用例**：挑 1~2 个最贴近核心主线的单元测试执行，目标是在数秒内获得绿灯反馈，确认本地环境和基本假设成立。

---

## 3. 基于 Git 历史定位系统重心

代码库的演进通常遵循幂律分布：大部分基础代码在写完后极少变动，而核心逻辑和关键妥协往往集中在少数高频变动的文件上。

### 3.1 识别架构热点
借助变更频率工具（如 `repo-mentor hotspots`）筛选近期高频变动文件：
- **高频修改 + 核心逻辑**：系统的承重关键，也是精读的首要入口；
- **高频修改 + 配置文件/Lock 文件**：属于构建噪音，主动过滤；
- **低频修改 + 稳定目录**：契约已经封板，阅读时只需关注对外暴露的接口。

### 3.2 创世提交（Genesis Commits）考古
面对迭代多年、抽象层层嵌套的大型项目，查看最早期的几次提交可以快速还原设计初衷：
```bash
git log --reverse --oneline | head -n 5
```
初版代码往往用最质朴的数据结构实现了核心想法，没有后期的兼容防御与特化逻辑，最容易看清作者的第一性解法。

### 3.3 识别时间耦合（Temporal Coupling）
如果某些原本属于不同模块的文件总是在同一次提交中被修改，通常暗示它们之间存在未被接口隔离的隐式依赖，这在研读时是值得重点记录的设计取舍或技术债。
