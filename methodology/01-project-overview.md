# 01. 项目全景侦察与开箱验证

## 目标
建立对未知开源或企业级代码库的宏观侦察方法论。在接触一个新项目的最初 5 分钟内，迅速理清其现实存在原罪、系统契约、核心解法与宏观拓扑，并在本地成功完成极简验证，建立端到端的宏观心智模型。

---

## 1. 认知第零定律：人话意图先行

在 AI 生成架构分析报告或工程师阅读代码时，最容易犯的错误是：**还没说清楚项目是干什么的，就直接扎进微观代码细节与行号**。

面对任何陌生的代码库，必须先回答三个最底层的业务与工程问题：
1. **现实痛点 (Real-World Agony)**：在没有这个项目之前，工程师或用户面临什么棘手的困境、性能瓶颈、机械重复或安全灾难？
2. **黑盒契约 (Black-Box Contract)**：
   - **输入事件 (Ingress)**：什么样的数据、配置或协议进入系统？
   - **交付产物 (Egress)**：系统最终返回什么结果？
   - **状态副作用 (Invariant Side-Effect)**：系统在外部介质（磁盘、数据库、网络）留下什么持久变化？
3. **第一性技术矛盾 (First-Principles Tension)**：系统核心权衡的两难是什么（例如：极致吞吐 vs 崩溃零丢失；轻量零依赖 vs 全格式富语义）？
   - **反思自问**：“如果用 30 行朴素脚本实现这个功能，会在什么极端场景下死得很惨？”那个让朴素脚本死掉的极端场景，就是该项目存在的全部理由。

---

## 2. 闭环验证：开箱即验 (Instant Validation)

只看文档不跑代码极易产生虚假理解。宏观概览必须附带**开箱即用的本地验证方案**：

1. **环境与极简构建**：
   - 给出无需冗长配置的构建或安装命令（如 `go build`、`pip install -e .` 或 `cargo build`）。
2. **代表性定向冒烟单测**：
   - 从核心路径挑选 1~2 个最具代表性的单测用例；
   - 必须带上精准过滤参数（如 `pytest tests/core/test_engine.py -k "test_dispatch"` 或 `go test -run TestCore`），杜绝运行动辄几十分钟的全量集成测试；
   - 目标是在 10 秒内看到绿灯输出，确保本地运行环境真实就绪。

---

## 3. 默认抓核心与宏观拓扑建模

系统的模块分工应当如实反映代码库自身的天然形态，拒绝千篇一律的生搬硬套：

### 3.1 自主识别项目最亮眼的特性
- **默认抓核心**：若未指定侧重点，自主识别该项目最亮眼、最不可替代的特性去展开（如果是精妙算法就突出算法，如果是架构设计就突出架构，如果是核心规则就突出规则），不做千篇一律的套话复述；
- **以用户为中心**：用户关注什么、提问偏向什么风格，就顺着用户的视角深入展开。

### 3.2 绘制带动态流向的架构拓扑图 (Mermaid)
- 使用 Mermaid 图表表达核心组件间的数据流动与交互依赖关系；
- 明确标出输入边界、调用流向与产物输出边界；
- 杜绝无箭头的孤立死方块，让读者一眼看清输入如何穿透系统。

---

## 4. 演进热点与渐进式切入路线

### 4.1 Git Churn 变更热点考古
- 代码库的演进遵循幂律分布：绝大部分缺陷与关键改动高度集中在极少数文件上；
- 运行确定性工具（`repo-mentor hotspots`）提取 Top-10 高频修改文件，锁定架构“台风眼”。

### 4.2 渐进式 3~4 站切入
规划清晰平滑的阅读次序：
1. **第一站：接入与上下文装配**（入口参数如何被转换为领域 Context）；
2. **第二站：核心调度与引擎**（主执行流、状态调度或核心算法）；
3. **第三站：高频变更业务逻辑**（近期活跃度最高的代码）；
4. **关键断点推荐**：推荐 1~2 个在调试器中最具观测价值的断点位置（附带文件与行号）。
