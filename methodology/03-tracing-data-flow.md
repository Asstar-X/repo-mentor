# 03. 向外追踪：链路场景与数据流转

## 目标
建立向外追踪跨模块协同、动态数据流经过程与上下文使用场景的方法论。专注解答“它在什么场景下被使用、最上游由谁触发、在链路中与谁协作、数据如何流经并改变形态、异常如何向外传播”，完成代码从静态结构到动态运行的认知跃迁。

---

## 1. 为什么向外看：摆脱孤立看代码的死胡同

很多时候把一个函数读了十遍依然一头雾水，原因往往不在于函数本身，而在于**不知道它在全系统中的生态位**：
- 它是常态下被高频调用的主通路，还是只在启动初始化时跑一次？
- 它是由用户直接触发的同步请求，还是后台 Worker 从队列捡起来的异步任务？
- 它的入参是从哪层上下文解出来的？它的返回值最终被谁消费？

向外看 (`/trace`) 就是为了把孤立的代码块放回活生生的调用链中。

---

## 2. 向外追踪的 5 步工作流

### 第一步：锁定真实业务场景
- 杜绝空对空谈论抽象数据，挑选一个最具有代表性的现实交互案例；
- 例如：“执行一条特定指令”、“传入一段特定格式的配置或输入”、“一次携带边界参数的调用”或“一次明确的状态触发事件”。

### 第二步：追溯最上游触发源 (Root Ingress)
- 顺着调用栈向上回溯，找出最上游的触发入口：
  - 是外部接口/协议解析入口？
  - 是 CLI 或脚本的主入口函数？
  - 是事件监听、调度触发点，还是被其他模块调用的公共 API？
- 明确标注最上游入口文件的物理路径与行号。

### 第三步：绘制上下游协同拓扑 (Mermaid)
- 使用 Mermaid 时序图（`sequenceDiagram`）或流程图（`flowchart LR`）；
- 清晰画出：**上游触发方 ➔ 当前目标模块 ➔ 下游承接方（产物交付/状态更新/输出适配）**；
- 标出各跳转步骤传递的核心方法调用与数据类型。

### 第四步：具象实例的端到端数据流转 (Payload Diff)
以选定的具象案例为例，记录数据在流经各阶段时的**形态演进与差分**：
1. **阶段 1 (入口形态)**：原始的输入参数、文本、配置或数据对象；
2. **阶段 2 (装配形态)**：被解析封装后的内部上下文或数据模型；
3. **阶段 3 (流经目标模块)**：目标模块对其进行的关键运算、状态改变或结构重构；
4. **阶段 4 (交付形态)**：最终输出给调用方的结果、生成的文件或生效的状态。

### 第五步：异常与失败如何在链路中扩散
- 如果当前模块执行失败或返回错误，整条链路如何响应？
- 是由上游调用方立即重试、降级兜底、还是直接中断整个生命周期向外抛出异常？
- 梳理异常传播链，明确系统在故障发生时的容错边界。
