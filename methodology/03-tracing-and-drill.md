# 03. 链路追踪与掌握度抽查指南

本指南作为 `/repo-trace` 与 `/repo-drill` 的思考工具，帮助把孤立的代码放回动态调用流中，并通过正反向问题检验真实理解深度。

---

## 1. 动态链路追踪方法（Payload Diff）

孤立看函数容易迷失，必须把它代入到真实的运行时生态位中。

### 1.1 锁定现实案例
挑选一个具有代表性的调用场景（如一条具体指令、一段特定配置、或一次正常交互），避免基于泛化概念空谈。

### 1.2 记录数据形态的演变（Payload Diff）
跟踪样本在流经各个节点时的具体变化：
1. **入口形态**：上游传入的原始参数或协议请求长什么样；
2. **上下文封装**：经过解析后，被打包成了什么内部上下文或数据实体；
3. **流经目标**：当前目标对象提取了什么字段、补充了什么信息、修改了什么状态；
4. **交付产物**：最后返回给下游或持久化的格式是什么。

### 1.3 观察异常传播路径
当目标内部处理失败时，错误是如何向外扩散的：
- 是立即终止链路向上传播，还是由上游捕获后降级兜底？
- 异常发生后，系统是否留下了未清理的半成品状态？

## 2. 掌握度抽查与答辩框架

看懂了逻辑并不代表真正吃透了设计。通过针对性的三类问题进行抽查和复盘：

### 2.1 意图题（Why — 为什么这么设计）
- **发问角度**：作者为什么专门写了一套抽象或调度机制，而不是用最简单直接的代码搞定？本质是在规避什么坑？
- **及格标准**：能讲清楚该方案相比最质朴的实现化解了什么矛盾，付出了什么代价。

### 2.2 流转题（Journey — 数据究竟怎么变的）
- **发问角度**：输入一个具体样本，经过此处的关键步骤后，具体的字段和状态发生了什么改变？下游最终拿到什么？
- **及格标准**：能指出 3~4 处具体字段或结构体形态的增减变化，而不是泛泛而谈“传递了参数”。

### 2.3 失效题（What-If — 极端场景下如何崩溃或自愈）
- **发问角度**：如果去掉某处核心校验，或者传入异常数据/遇到资源耗尽，系统在什么时机崩溃？有没有降级方案？
- **及格标准**：能指出代码里的具体防御点，或者推演缺失防护时的实际故障场景。
