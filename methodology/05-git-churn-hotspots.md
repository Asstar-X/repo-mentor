# 05. Git 变更热点与演进考古

## 目标
建立基于版本控制历史的实证架构分析方法论。通过 Git 提交日志与修改频次（Git Churn），利用幂律分布快速定位系统演进最活跃的“台风眼”，结合创世提交考古还原作者最纯粹的原型设计初衷。

---

## 1. 软件演进的幂律分布 (Git Churn Power Law)

在真实的软件工程中，代码并非均匀演进的：
- 80% 以上的代码在创建后极少再次改动（如配置解析、协议序列化、通用工具库）；
- 核心演进、架构妥协与绝大多数历史缺陷，**高度集中在不到 10% 的高频变动文件上**。

通过分析提交历史，可以从根本上避开“从第一行看到最后一行”的低效泥潭，直击系统真正的重心。

---

## 2. 变更热点与架构台风眼定位

运行确定性分析命令定位近期修改最频繁的文件：

```bash
# 提取近 300 次提交中修改频次最高的 Top-10 文件
repo-mentor hotspots <target_path> --commits 300 --top 10
```

在分析热点输出时，进行交叉比对：
- **高频修改 + 核心算法/调度**：这就是整个系统的“承重墙”或“台风眼”，必须作为精读研读的最高优先级；
- **高频修改 + 配置文件/文档**：排除噪音，主动过滤掉频繁变动的依赖锁文件（如 `package-lock.json`、`Cargo.lock`）；
- **低频修改 + 核心目录**：说明该模块已高度稳定（或已封板），阅读时重点关注其向外暴露的接口契约即可。

---

## 3. 创世提交 (Genesis Commits) 考古

大型成熟项目经过多年的功能迭代，往往包裹了大量的边缘防御与特化逻辑，容易让人迷失方向。

**还原设计初衷最有效的方法是：看它最初的样子**：
1. **查看最早的几次提交**：
   ```bash
   git log --reverse --oneline | head -n 5
   ```
2. **检视初版核心文件**：
   - 作者在最初的 100~300 行代码中，用什么最质朴的数据结构实现了核心想法？
   - 初版代码往往没有后来的复杂抽象，最容易看清系统最纯粹的第一性解法。

---

## 4. 演进轨迹与技术债识别

高频变更往往伴随着技术债的累积：
- 如果一个文件在每次提交中都在被修修补补，通常意味着它的职责过重（God Object）；
- 如果多个文件总是同时出现在同一个提交中（Temporal Coupling 隐式时间耦合），说明它们之间存在未被接口隔离的隐式依赖；
- 在写架构白皮书时，指出这些演进热点与耦合风险，能为团队提供极具工程价值的重构洞察。
